# How this knowledge base is organised

This file is for humans. The harness starts from `00-overview.md`, which is loaded at
the start of every session.

```
knowledge/
  00-overview.md            L0: the overall picture. Read first, always.
  context/                  the company, the teams, workflow vs app, how a workflow runs, why subsystems
  dependencies.md           generated from build files: who depends on what, at which version

  workflow-development/     system: how a workflow is built and run      (workflow developers)
    workflow/               the runtime roles of one variant image (WORKER_MODE)
    workflow-library/       platform-core, wf-scaffolding, variant-scaffolding
  app-development/          system: how an app is built and run          (app developers)
    app/                    fb-worker and the app contract, the base image
    app-library/            rf-fb-worker-core
    ui-synthesizer/
  subsystems/               system: the services that act on running workflows and apps (support)
  communication/            system: the task fabric, AKST and the task SDKs (everyone)
  reporting/                system: platform events, audit, customer webhooks (hub / reporting)
  platform-delivery/        how everything is configured and shipped

  flows/                    task paths across subsystems (authored; evidence re-verified by sync)
  contracts/                interfaces and message schemas, by name
  tables/                   database tables, by name
  constitution/             philosophy, ownership, glossary, status vocabulary: the full rules
  known-issues/             defects that a semgrep rule re-verifies at the current release
  runbooks/                 how to do recurring kinds of change
  in-flight/                designs NOT yet released. Never read as current behaviour.
```

## The levels

| Level | What | Example |
|---|---|---|
| L0 | `00-overview.md`: philosophy, the map, dependencies, the subsystem picture, which areas a kind of change touches, how to traverse | always loaded |
| L1 | `<system>/README.md`: what the system is for, its areas or members | `subsystems/README.md` |
| L2 | `<system>/<area>/README.md`: one area and its members | `app-development/app-library/README.md` |
| L3 | a component document | `subsystems/workflow-ops.md`, `subsystems/workflow-ops-grpc-api.md` |
| L4 | extracted facts for a component: entry points, RPCs, calls, tables, dependencies | `kb_component("workflow-ops")` |

Cross-cutting material (flows, contracts, tables) is read by exact name, from a link in an
L1-L3 document.

## Rules that keep it clean

1. **One home per thing.** A component's document lives in the folder of the system that
   owns it (catalog `system:`).
2. **Authored and generated are never mixed in one file.** The README member tables and
   `dependencies.md` are generated by `tools/gen_system_readmes.py`; regenerate rather
   than edit them. Everything else is authored.
3. **Nothing is found by keyword search.** Every document is reachable by following links
   down from `00-overview.md`.
4. **Unreleased designs live only in `in-flight/`.**
5. **A known issue stays only while a rule re-verifies it** (`rules/`, `tools/patterns.py`).
   Disagreement cards that no longer verified were archived on 2026-11-14.
6. **No deploy-time values.** Kafka topic names and environment values are configuration,
   not knowledge.
